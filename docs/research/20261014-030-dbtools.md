# 20261014-030 – Database tools for project databases (P27)

## Question
Which database-side mechanisms make the P27 tools safe for *project* databases: read-only queries that cannot write,
throw-away sandbox databases for generated migrations, consistent backups and a real restore test?

## Why needed
`hermclaw.dbtools` (db_introspect, db_query_readonly, db_migration_generate, db_migration_apply_sandbox, db_backup,
db_restore_test) acts on databases of user projects; correctness must not depend on the model's SQL.

## Relevant facts
- A PostgreSQL transaction started with `SET TRANSACTION READ ONLY` refuses every write (also via functions) –
  combined with a lexer-based single-statement check and a function denylist (`pg_terminate_backend`, `lo_import`,
  `dblink`, …) and `statement_timeout`, a read-only query cannot change data (verified against PostgreSQL 16.15).
- SQLite opened with `file:…?mode=ro` (URI) plus an authorizer that denies writes/ATTACH is read-only (SQLite 3.45.1).
- `pg_dump -Fc` + `pg_restore --no-owner --exit-on-error` into a fresh database, then row counts per table, is a real
  restore test (same approach as Hermclaw's own backup, R-022).
- Migration frameworks are detected from files (alembic.ini/env.py, manage.py + migrations/, numbered SQL); Alembic
  runs against a sandbox database URL injected into the environment.

## Decision / recommendation for Hermclaw
Targets in optional `/etc/hermclaw/databases.yaml` (`config/databases.example.yaml`), DSNs only as secret references,
production targets always read-only; migrations are applied only to throw-away sandbox databases on a non-production
server (role with CREATEDB + CREATEROLE), commands of the project's migration tool run in the execution sandbox
(`hermclaw.runtime.ops.WorkspaceExecutor`); sandboxes of crashed runs are dropped at scheduler start.

## Implementation consequences
`hermclaw/dbtools/*`, `docs/architecture/dbtools.md`, 193 tests against real PostgreSQL 16 / SQLite / alembic;
INSTALLATION.md documents `databases.yaml` and the sandbox server role.

## Open risks
A project `env.py` that ignores `sqlalchemy.url`/environment could migrate another database – the sandbox role has no
rights outside its sandbox database, and production DSNs are never passed to migration commands.
